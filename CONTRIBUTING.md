# Teapot Service - Contributing Guidelines

## Section 1: The Preamble
Welcome to the contributor guidelines for the Teapot Service. Before you even consider opening a Pull Request, you must read this document in its entirety. This document serves as the absolute source of truth for our enterprise operations. Any deviation from these rules will be met with immediate closure of your PR, accompanied by a sternly worded automated response.

## Section 2: Code of Conduct
As an enterprise refusal engine, we expect our contributors to maintain a high level of professionalism when writing code that does nothing.
1. Do not propose features that actually brew tea.
2. Do not attempt to add water to the teapot.
3. Treat all HTTP 418 errors with the reverence they deserve.

## Section 3: The Pull Request Lifecycle
The lifecycle of a PR in this repository is designed to simulate a highly bureaucratic enterprise environment.
### Stage 3.1: Ideation
Before writing code, you must submit an RFC (Request for Complaining) detailing why your new refusal method is superior.

### Stage 3.2: Implementation
When implementing your change, ensure you have mocked at least three deeply nested spans in OpenTelemetry.

### Stage 3.3: Code Review
Your code will be reviewed by the Teamaster, the Admin, and the Guest. All must approve. The Guest never logs in. Therefore, your PR will remain open indefinitely.

## Section 4: Variable Naming Conventions
- Variables MUST be camelCase.
- Variables MUST explicitly state what they are not doing. (e.g., `teaNotBrewed`, `emptyWaterReservoir`).
- Interfaces MUST begin with `I` and end in `Refusal`.

## Section 5: Testing
You are required to write tests that assert nothing happens. If an exception other than `TeapotException` is thrown, your build will fail. Coverage must remain at 100%.

## Section 6: Diagramming
All architectural changes must be accompanied by a Mermaid diagram demonstrating how the request enters the system, is validated, and subsequently refused. We rely heavily on visualizing exactly how nothing changes state.

## Section 7 through 99
We take the refusal to brew coffee very seriously. Any commit containing the word 'coffee' without the word 'rejection' will trigger a cascading failure simulation in the CI pipeline. Remember that this goes all the way to Kubernetes manifests, although they are currently optional.

Thank you for your anticipated compliance.
